## Going forward

**F-36 is closed**, which completes a round trip worth naming: it was entered the moment it was understood,
carried the reason its fix was *not* folded into the slice that found it, named the milestone it would land
before, and landed there. That is the ledger working as intended — a finding is recorded when it is seen, not
when it is convenient.

**F-37 is the ledger's blind spot, twice.** It is the same shape as F-35: a requirement stated plainly in
`REQUIREMENTS.md`, a mechanism described in the specification, and no line in §19's build order claiming it —
so every milestone review passed, because every milestone had done what its own list said. Two findings with
one cause is a pattern rather than an accident, and the cheap guard is a habit rather than a process: when a
requirement section names a capability, §19 should name the milestone that owns it, and a section that no
milestone claims should be visible as such. Both gaps were found the same way in the end — by somebody
trying to *use* the thing, not by anybody reading the documents.

**F-50 is F-38's shape at the deployment boundary, and it is worth naming as its own class.** F-38 was four documents agreeing about something no code did. F-50 is four documents agreeing about something the code did correctly, where the *transport between the operator and the code* discarded it — and the whole suite passed, legitimately, because every test constructs its own options object rather than receiving the one a container hands over. The general form: **a value crosses a boundary this project does not test, and the far side of that boundary has a plausible default.** Silence is then the expected output of the defect. `compose.yaml` was the instance; the class also contains build arguments, workflow `env:` blocks and anything else where one file names a key that another file must name identically. The cheap guard is the one applied here — derive the set from whichever side is authoritative, and assert the restatements — and it is worth reaching for wherever two files have to spell the same string.

**F-38 is a third shape, and this ledger was part of it.** F-35 and F-37 were capabilities that a requirement
stated and no milestone claimed. F-38 is the opposite failure: S§15 stated the rule, S§19 named the milestone,
`OPERATIONS.md` §6 wrote the runbook, and **F-16's row right here listed "The Data Protection keys volume is
backed up alongside the database" under *Embodied in*** — four documents in agreement about something no code
did. Nobody was wrong to trust them. The row was written when the decision was made, and a decision is not an
implementation; "embodied in" was recording intent in a column reserved for fact.

The guard is not more documentation. It is that a claim about behaviour should be checked by something that
runs. The key ring is now captured by a script rather than by a reminder, its presence is a gate rather than a
sentence, and that gate executes on every push — so the next time this drifts, the build goes red instead of
the ledger staying green. Where F-36's lesson was *record a finding when you see it*, F-38's is *a row in the
embodiment column should name something executable*.

**F-39 is the fourth of a kind, and the ledger caught it before a user did.** F-35 and F-37 were capabilities a requirement stated and no milestone claimed, both found by somebody trying to *use* the thing. F-38 was a rule four documents agreed on and no code did, found by somebody finally executing a runbook. F-39 is F-35's shape again — R§1 and `CONTRIBUTING.md` both assumed a freedom the application did not deliver — but it was found by *reading the tree against what a tag would make true*, which is the first time that habit produced anything. That is worth recording as a habit rather than an anecdote: **the moment before publishing is a distinct review, because publishing changes who the audience is.** Questions that had obvious answers while one person ran one instance ("which build is this?", "who would ever need the source from us?") stop having them the moment somebody else can `podman pull` the thing.

F-38's lesson — *a row in the embodiment column should name something executable* — was applied here without being asked for. The offer's presence is a CI gate, not a sentence: `boot-smoke` fails unless `/source` names the commit it was built from. If the stamp chain breaks, the build goes red rather than the page quietly reporting "Not recorded" for a year.

**F-42 is the fifth shape, and the first about the repository rather than the work or the workshop.**
F-35, F-37 and F-39 were capabilities a requirement stated and no milestone claimed. F-38 was a rule
four documents agreed on and no code honoured. F-40 was the transport between a correct specification
and correct code. F-42 is the *container*: the tree was right, the gates were green, and a settings
page disagreed with a sentence in `CONTRIBUTING.md` — a sentence that had been false for as long as it
had existed, because nothing in a repository can inspect its own settings.

That generalises into a rule worth keeping, and it is narrower and more useful than "check your
settings": **a document states policy, never platform state.** "Nothing filed here is triaged" is a
commitment, it is true wherever it is read, and it survives somebody toggling a checkbox. "The issue
tracker is off" is a claim about a checkbox, verifiable only from outside the repository, and it went
wrong in the only direction that mattered — the door it declared shut was the *one* door standing open,
and it was a public one.

Two habits are worth naming because both of them worked here. F-39's — *the moment before publishing
is a distinct review, because publishing changes who the audience is* — found this, one layer out from
where it found F-39: publishing changes not only who reads the version number but **who finds the
defects**, and this repository had answered that population by closing every door and mislabelling the
open one. And F-38's — *a row in the embodiment column should name something executable* — was applied
for the third time without being asked for, which is the point at which a lesson stops being a lesson
and becomes how the project works. The disclosure channel's existence is a blocking gate, and the
sentence that caused the finding is now a pattern the gate refuses.

What that gate cannot do is the honest limit of this fix, and it is recorded rather than papered over.
Its platform half is advisory and its tree half cannot see a settings page at all, so **enabling
private vulnerability reporting and setting the repository description remain operator actions** — the
gate will WARN about them on every run in CI and will never fail on them. That is a gate reporting a
finding on every run, which this project has twice argued against. It is accepted here for a reason
that did not apply either previous time: the finding is *about* something outside the tree, so there is
no commit that could clear it, and a WARN that persists until somebody clicks a checkbox is exactly as
loud as that situation deserves.

**F-40 is the first finding about the workshop rather than the work.** F-35, F-37 and F-39 were capabilities a
requirement assumed and no milestone claimed. F-38 was a rule four documents agreed on and no code honoured.
F-40 is neither: the specification was right, the code was right, and the *transport between them* damaged
twenty-one files. That is a category this ledger had not recorded before, and it generalises further than the
one incident — every delivery into this repository arrives as text produced by a tool, and no tool that
produces text is incapable of producing slightly wrong text.

The lesson is narrower than "check your work" and worth stating precisely: **when a format carries both content
and decoration, only the content's declared length is authoritative.** `export.sh` publishes an exact byte count
for every file it emits and a separator after it; a reader that trusts the separator will be wrong exactly as
often as a file ends near one. Nothing in the dump format needed fixing — the byte count was always there.

And the corollary, which is what actually landed: **the gate belongs at the point where the damage is cheap to
name.** MSBuild eventually reported the problem, but it reported it as `Data at the root level is invalid`, four
verbs deep, with no indication that twenty other files shared the fault. `scripts/check_tree.sh` names all of
them, by line, in under two seconds, before the SDK is even asked for an opinion.

**F-41 is F-40's own gate failing, and the pair is the finding.** F-40 argued that a check belongs at the point where damage is cheap to name. F-41 is the bill for that argument: the gate landed, and the next run of `scripts/ci_local.sh` reported 1321 problems on a tree in which every file was correct — 1276 of them the two committed context dumps, whose structure is the separator the gate exists to forbid, and 45 of them intact `.tar.gz` archives accused of being truncated. Because gate 1 is first, the four gates behind it did not run at all. A gate that cannot pass on a correct tree is worse than no gate: it is a gate that has to be bypassed, and the four real checks behind it went with it.

The narrow lesson is about **exemption symmetry**. The gate exempted `export.sh` because writing separators is that script's job, and stopped there — but the separators live in the directory `export.sh` *writes into*, which `export.sh` itself already excludes from its own output for the same reason. Exempting the producer and not the product was half a rule, and half a rule is the shape most scope bugs take.

The wider one is about **who decides scope**. Gates 1 and 2 were binary-safe by accident, because `grep -I` declines to match in a binary file; gate 3 was not, because `tail -c 1 | wc -l` has no such notion. Three gates over one file set held two different beliefs about what a file was, and nothing made them reconcile. The fix is not three guards but one predicate all three consult — and it asks `grep -I` rather than an extension list, because the extension list would have been wrong about the `.zip` files on the day they were added. **When several checks share a file set, the set is the thing to define once; a per-check guard is a per-check opinion waiting to diverge.**

And a rule for gates generally, which this one now follows: **a gate must report what it declined to inspect.** "Checking 412 tracked files" was true on the run that failed 1321 times, and it was the least useful true sentence available. Skip counts beside the total are what make a quiet gate's silence mean something.

New issues enter this ledger as fresh `F-nn` rows — finding, ruling, embodiment — landed in the **same commit** as the change they describe, together with the matching `REQUIREMENTS.md`, specification, and ADR edits (atomic documentation, R§10 · S§18).

**F-45 and F-46 are the sixth and seventh shapes, and the pair of them says something about gates.**

F-45 is the first finding here about a file that *should have existed and never had*, where every file
that did exist was correct. `.gitignore` names `.env`, the key ring and every dump, and it is right about
all of them; it simply answers a question — what belongs in a commit — that nobody had noticed was a
different question from what belongs in a build context. Five gates read `git ls-files`, so the whole
class was invisible by construction: the files at issue are git-ignored *on purpose*, and being
git-ignored is exactly what made them dangerous. The habit is narrow and checkable — **when a tool is
handed a directory, ask what it was handed, not what is committed.**

F-46 is the more uncomfortable of the two, because the defect is in a repair this ledger recorded as
complete. Slice 20 wrote the rule down in three places — a document states policy, never platform state —
and then enforced it with a list of six phrasings about the repository page. The sentence that broke the
rule was about the *package* page, it was already in the tree on the day the gate landed, and the gate
reported "none" and was believed. **A rule stated as a rule and enforced as a list of examples is
enforced as a list of examples**, and the gap between the two is invisible precisely when the gate is
green — which is the sentence F-43 and F-44 earned in Slice 21. Three findings in two slices about checks
whose name was true and whose content was narrower than the name is not three accidents.

The guard is not "write better lists". It is that **the list belongs to the rule** — kept beside it, with
the reasoning, so that extending it is part of understanding the rule rather than a chore for later — and
that where the domain permits one, the assertion should be an allow-list rather than a deny-list. F-45's
fix is the same shape for the same reason: `.dockerignore` names what may enter rather than what may not,
because the population that matters is always the thing nobody has thought of yet.

F-38's lesson keeps earning its place. Both rows name something executable, and F-45's runs **in the build
itself** rather than only in CI — the first time that distinction has mattered, because the machine most
likely to have a key ring sitting in the tree is the operator's, and the operator does not run CI.

**One procedural finding, recorded against this file rather than against the tree.** Slice 21 shipped
F-43 and F-44 as working code and left them out of this ledger and out of Appendix A entirely; the only
account of either was a `docs/_append/` file that had not been merged. That is the atomic-documentation
rule (R§10 · S§18) broken by the delivery that invoked it, and it is why both rows above are dated to
Slice 21 and landed in Slice 22. The mechanism that allowed it is being retired at the same time:
`docs/BUILD_PROGRESS.md` is delivered as a whole file from here on, so there is no separate artefact left
to forget.

**F-49 is the eighth shape, and it is the one this ledger had no row for: a control nobody decided on.**

Every finding above is something absent, something wrong, or something narrower than its name. F-49 is
a mechanism that was **present and working and unowned**. The framework put a Content Security Policy
on this application's responses in M1 and it was still there four milestones later, protecting against
a real attack, covering one directive on a subset of responses, and appearing in no document, no test,
no ADR and no conversation. Nothing was broken. Nobody could have told you what it covered.

The habit that falls out of it is narrow and checkable, and it is the mirror image of F-47's. F-47 said:
*when a check or a rule is named for a category, go and compute the category.* This one says: **when a
framework ships a security control on your behalf, find out what it covers and write that down —
because the reach of a protection you did not choose is exactly as unknown as the reach of one that
does not exist.** The way it was found is worth keeping too, and it is F-39's habit at one more remove:
the moment before publishing is a distinct review. F-39 asked what a tag makes true about the program,
F-42 about the repository, F-45 about the artefact. This asked what it makes true about the *response* —
a guest's browser is the last thing in the chain and the only one that never consented to anything.

And a second-order note, recorded because it nearly went the other way. The obvious policy —
`connect-src 'self'` — would have been correct-looking, would have passed every unit test that could be
written about the header, and would have refused the Blazor circuit's WebSocket on every plain-HTTP
origin: a bare `dotnet run` and all fifteen §16.3 scenarios. What would have caught it is Slice 23's
work: `data-live` and `data-loaded` on six surfaces, and four harness barriers that demand both. A
policy that kills the circuit is a policy under which no surface ever reports `data-live='true'`. That
is the second time in two slices that the useful thing about a gate was a failure it would catch that
nobody built it for.

**F-47 and F-48 are the same sentence at two scales, and the sentence is now four slices old.**

F-43's engine selection was named for what it needed and asked `PATH` instead. F-44's barrier was named
for a loaded board and matched a loading one. F-46's rule was named for platform state and enforced six
phrasings about one settings page. F-47's fix was named for *the live surfaces* and meant the five
somebody had written down. Every one of them was green while being narrower than its name, and every
one was found by asking what the name would mean if it were taken literally.

That is worth stating as the habit it has become: **when a check or a rule is named for a category, go
and compute the category.** Not "review the list" — compute it, from whatever actually decides
membership. Here that was eleven lines of `App.razor`, and it produced a surface the list had never
contained. F-46 said the list belongs to the rule; F-47 is the next step, which is that where the rule
can be executed, the list should not exist at all. `LiveSurfaceContractTests` keeps exactly one list —
the expected interactive set — and compares it against the set the rule produces, so the two can only
agree by both being right, and adding a surface is a decision somebody makes rather than an omission
nobody notices.

**F-47 also settled a question this ledger had not been asked before: what makes two things the same
rule.** The obvious reading of "give the other surfaces the bit `/counter` has" is to copy the
expression, and on `/display/{table}` that would have published an attribute reading `true` whenever
its element existed — no defect, no failing test, and a barrier no stronger than the one it replaced.
The uniform thing is the *question* a bit answers, not the code that answers it, and a contract that
pins the expression forecloses the one surface where the question has a different answer. So §11.10
pins `data-live` exactly, because "did a circuit render this" has one correct answer in this framework,
and pins only the shape of `data-loaded`, because "does this markup have what the surface is for" does
not. A rule that cannot admit a justified difference gets copied past the case that mattered.

**F-48 is small and is recorded at full weight on purpose.** A version number in a header is not a
defect worth a paragraph; a defect that was found, corrected, explained in the correcting document, and
then repeated is. The v1.3 entry did everything right except leave something behind that runs, and
seven versions later the same two fields disagreed again. That is F-38's lesson arriving from the least
dramatic direction available — *a row in the embodiment column should name something executable* — and
the cost of honouring it here was two assertions in a file that already knew how to find the repository
root.

**F-51 and F-52 were found by the same act, and it is one this project had never performed: running the
documented command on a second machine.**

Not a review, not a reading, not a gate — an execution, somewhere other than where the code was written.
F-51 is what the canonical engine says when `compose.yaml` reaches a host whose registry configuration
Fedora had been supplying for free. F-52 is what an operator needs on a host that is not a workstation,
which two documents had described as impossible. Neither is subtle. Both were invisible from inside the
machine that had every gate green, because every gate in this repository asks a question about the tree
and the one question nobody had asked was *does this work anywhere else*.

That is worth stating as the habit the ledger has been converging on from the other direction. F-42 asked
what the repository looks like from outside; F-46 asked what the moment before publishing looks like;
F-50 asked what an operator who is not this maintainer actually receives. This asks what a **second
machine** actually does — and it is the cheapest of the four, because the answer arrives as a stack trace
rather than as a judgement.

**The uncomfortable half of F-51 is that the rule was already written down.** `scripts/restore_drill.sh`
has carried the fully-qualified-image reasoning since Slice 16, in a comment, about a scratch container.
A maintainer solved this problem once, in the narrowest place it appeared, and the canonical stack — the
one ADR-0004 names, the one OPERATIONS documents, the one a fork will run — kept the defect for ten more
slices. F-46's lesson was that a rule enforced as a list of examples is enforced as a list of examples.
This is the step before it: **a rule discovered on one example and never stated as a rule at all.** When
a comment explains why a value has to take a particular form, the question to ask immediately is where
else that value appears.

**F-52 also settles what to do with a document that is accurate and misleading.** The sentences were true
of the script they described; deleting them would lose the reason the foreground script cannot detach,
which is genuinely useful. So they are corrected in place, and the correction names the thing the original
left implicit — *this script is the owner* — because an incidental property stated as a law is only
findable once somebody separates the two.

**F-53 is the third finding from the same act, and the first one the act had to be repeated to find.**
F-51 and F-52 came from running the documented command on a second machine. F-53 came from running it
again, on the same machine, after F-51's fix — because F-51 failed early enough to hide everything
behind it. That is not a new habit so much as a correction to the one just recorded: *running it
elsewhere* is not an event, it is a loop, and a second machine will keep producing findings for as
long as it keeps getting further through the procedure. The honest expectation after this slice is that
the next run gets further still and finds the next one.

**And F-53 names a failure mode this ledger had no entry for: the defect whose whole manifestation is
the absence of output.** Every earlier silent finding was silent because something plausible filled the
gap — F-50's compiled-in default, F-42's open issue tracker, F-44's prerendered markup. This one is
silent because the loop that hangs logs at debug level and the condition it is waiting for appears
nowhere in the output. There is no wrong answer to notice, no page that renders incorrectly, no
mismatched string: there is a command that stops. The general form is worth carrying: **when a tool
does nothing, the question is not what it did wrong but what it is waiting for**, and the place to
answer it is the tool's source, not its output. That is what reading podman-compose 1.3.0's
`compose_up` produced in about ten minutes, having produced nothing in the hour before.

**F-57 is the first finding in this ledger that the previous slice's own tooling found, and that is the
only reason it is here.** F-55's fix printed two container logs side by side for the first time. The five
`Configuration error:` lines and the `initdb` loop had both been happening for hours across three
sessions; neither had ever been on screen. Put together they name one cause, and it takes about ten
seconds to see it. The lesson is not about compose: **a defect often survives because nobody has ever
seen its two halves at the same time**, and printing the evidence is cheaper than any amount of
reasoning about it. Every earlier finding here was found by a person reading the tree or running a
command; this one was found by a diagnostic that had existed for one day.

**And it settles what F-51's class actually is.** F-51 was a *value* this repository wrote in a form the
canonical engine could not resolve. F-57 is a *feature* of that engine which does not work, on a file
that is correct by every reading. Both produce "the canonical stack does not start on a supported host",
and only the first is fixable by editing the file — which is why the answer here is a check that asks
the engine and refuses, rather than a rewrite of `compose.yaml` guessing at which forms are safe. The
general rule, now in §14.1: **where the stack depends on the engine doing something, ask whether it did,
and do not spend twenty minutes of work first.**

**F-55 is F-53's fix producing F-53's shape in the opposite direction, in the same file, one slice
later.** F-53 was a wait with no deadline. Slice 27 put deadlines on every compose call and wrote,
in the same script, a 300-second wait that polled HTTP without once asking whether the thing it was
polling still existed — and then printed a success banner and exited 0. The two failures look like
each other and need opposite fixes: a deadline stops a wait that *cannot end*, and only a liveness
check stops a wait that *cannot succeed*. Both were reasoned about carefully; neither reasoning
covered the other case. The general form is worth carrying, because it is not specific to shell
scripts: **a bound on how long you will wait is not a bound on how long you will be wrong.** Anything
that waits should be asked both questions — what makes this end, and what would make this pointless —
and a wait that cannot answer the second is a wait that will eventually report success over a corpse.

**And F-55 records a rule about exit codes this project had not stated.** The script's status was a
report on the script: it had done its steps, so it returned 0. The operator's question is not whether
the steps ran, it is whether the instance serves — and `time bash scripts/dev_instance.sh` is how the
question gets asked. A command whose exit code answers a question nobody asked is worse than one with
no exit code at all, because a `&&` chain believes it. So the rule is now written down in §14.3a: the
status of a bring-up is a claim about the instance, and the instance is left running when the claim is
negative, because the containers are the evidence and reading them destroys nothing.

**F-56 is the third occurrence of F-51's shape, and the third is where a pattern stops being an
accident.** F-51: `restore_drill.sh` fully qualified its image and the stack it rehearses did not.
F-46: a rule stated generally and enforced as a list of examples. F-56: `run.sh` dialled the loopback
literal since M1 and the two tunnel helpers named a hostname. Every one of them is a maintainer
reasoning something through correctly, in one file, and not asking which other files the reasoning
applies to. The cheap habit, and it is cheaper than the audit it replaces: **when a comment explains
why a value is what it is, grep the tree for the other places that value is written.** F-51's comment
said *"fully qualified so a short-name registry prompt cannot hang a drill"* and one grep for
`postgres:17` would have found the stack. There was no comment at all beside `run.sh`'s literal, which
is the smaller half of the same finding — a choice with a reason and no note of it is a choice nobody
can generalise from later, including the person who made it.

**F-54 is F-38 at one-tenth the stakes, and it is the second time this file has been part of the
defect.** F-38 was four documents agreeing that the key ring was backed up, one of them F-16's row in
this ledger, under *Embodied in*. F-54 is O§2 and the same F-16 row agreeing that `.env` is created.
The column is the problem, and it was diagnosed correctly in F-38's own closing paragraph — *"the row
was written when the decision was made, and a decision is not an implementation"* — so the lesson here
is only that the diagnosis was not applied backwards over the rows that already existed. **Every
pre-F-38 row in this file names embodiments that were, at the time of writing, intentions.** Nobody has
audited them. F-54 is one of them, found by accident, and the cheap version of the audit is the habit
this project already has: when a document cites a row in this file for a *behaviour*, check the
behaviour, not the row.

**F-59 is the first finding in this ledger that this project did not find, and that is the whole of its
lesson.**

Every shape recorded above was found from inside. F-36, F-40 and F-48 were found by reading the tree.
F-38 was found by executing a runbook. F-39, F-42, F-45 and F-46 were found by asking what a tag would
make true, one layer further out each time. F-51, F-52, F-53 and F-55 were found by running the documented
command on a second machine, four slices in a row. F-57 was found by a diagnostic that the previous slice
had added. Every one of those is a habit, and the habits work.

F-59 was found in about ninety seconds by somebody who was handed the application and tried to use it.
All fifteen §16.3 scenarios were passing. Every gate was green. 1066 tests. `ci_local.sh --with-all` had
cleared. And four administration pages could not be operated on the device R§1 has named since rev 1.

The generalisable statement is narrow and uncomfortable: **a project can only find the defects its own
premises admit.** Not "test more" — the tests were correct, and the one that would have caught this could
not have been written, because no document asked for the property it would have asserted. R§1 said guests

So the habit is: **show it to somebody.** Earlier than feels ready, which is what happened here — this was
shown before user testing was thought to have started, and it produced one defect and one enhancement
request, of which the defect was the more valuable. And the corollary, which is F-38's lesson arriving from
a new direction: when an outside report names a property, write the property down as a rule before fixing
the instance, because the instance was four pages and the rule is every page from now on.

**F-58 is the third occurrence of a defect this file has twice recorded as fixed, and the third time it
was the scope of the fix rather than the fix.** F-48's row says the gate asserts *header-matches-newest*
and *entries-descend*, and both are true; what the row does not say is which file. A `const string` naming
one path reads as configuration rather than as a scope decision, and that is why nobody read it as the
list it was. F-46 already said that a rule enforced as a list of examples is enforced as a list of
examples. This adds the sharper corner: **a list of one does not look like a list**, so the general
statement is worth having in the form F-47 gave it — where the rule can be executed, the list should not
exist at all. Both F-46 and F-58 were repairs whose *scope* was narrower than the sentence describing
them, and in both cases the sentence was written by the person who chose the scope, in the same commit.
